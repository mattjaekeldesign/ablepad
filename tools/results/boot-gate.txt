# --- what this establishes ---
#
# The EVO probe works on real hardware. Reading
#   HKLM\SYSTEM\CurrentControlSet\Services\audientusbaudio\Enum
# found VID_2708&PID_0007 bound, in 0.03 ms. That is the check running every tick
# with no measurable cost, versus ~1 s for Get-PnpDevice.
#
# A check that starts failing and later passes is reported both ways. The launchpad
# check failed at gate start (the service had not opened the device yet) and logged
# "now passing" when it did. Boot conditions that arrive late are not punished for
# being slow -- which matters, because USB enumeration order at cold boot is exactly
# the kind of thing that is slow and out of our control.
#
# Each distinct failure is logged ONCE, not once per tick. At 30 Hz over a 90 s
# deadline the naive version would write 13,500 lines before giving up.

# --- what is NOT yet established ---
#   * that all five pass together and the gate transitions BOOT -> SET_BROWSER.
#     Needs Ableton running and bound to the EVO.
#   * that the EVO probe goes FALSE when the interface is unplugged. The registry
#     key is documented to behave that way and read correctly while attached, but
#     nobody has watched Count drop to zero. Flagged in windows/probes.py.
#   * the FAILED path: gate expiring at 90 s and driving the rig into Error Mode.

# --- one design flaw found and fixed between the two runs ---
# The settle check originally timed from when the GATE first saw Ableton's process.
# The rig controller can restart while Ableton has been up for an hour -- a crash, a
# Task Scheduler retry, a manual run -- and every one of those restarts would sit on
# the splash screen for the full 25 s waiting for something that finished long ago.
#
# Now it reads the process's own create_time. Boot took 380 ms instead of 25 s.
# Still a guess (process age is not "set loaded"), just a less wrong one, and free.

# --- one cost measured, understood, and accepted ---
# First run: 7 overruns in 13 s. The memory_maps probe costs ~13 ms and each cache
# refresh pushed one tick past its 33 ms budget.
#
# Second run: 1 overrun. Not because the probe got cheaper -- because boot completed
# in 380 ms, and boot_tick() returns immediately once the state leaves BOOT.
#
# So the hitch is confined to the splash screen, where nothing is being performed.
# 13 ms of late LED painting while waiting for Ableton is invisible; the same hitch
# mid-set would not be. Accepted rather than engineered around.

# --- an open UX question, not a bug ---
# Boot completing in 380 ms CANCELS the 4 s boot-rain intro partway through. Correct
# behaviour (do not make the player wait for decoration) but it looks abrupt. The
# alternative -- let the intro finish before switching -- costs 3.6 s of dead time on
# every boot. Decide deliberately; do not let it drift.
