# ============================================================================
# THE MEASUREMENT THAT MATTERS: boot_settle_s is 6x too long for this set
# ============================================================================
#
# Ableton bound the EVO's ASIO driver 4.1 SECONDS after launch. The settle timer
# then held boot for another 21 s for no reason anyone can point at.
#
# boot_settle_s = 25 was an admitted guess. It is now a guess with one data point
# against it -- for a nearly empty emergency set.
#
# DO NOT just lower it to 5. The emergency set is trivial: no plugins, no samples,
# no NAM model. A real performance set loads a Neural Amp Modeler, IRs and whatever
# else, and "audio device bound" happens EARLY in Ableton's startup -- well before
# a heavy set is playable. Tuning to the emergency set would produce a rig that
# declares itself ready while a real set is still loading.
#
# What to do instead:
#   1. Boot with the REAL performance set and stopwatch from launch to first
#      playable note. That number, plus margin, is boot_settle_s.
#   2. Consider whether ableton_audio passing is a better readiness signal than a
#      timer at all. It is evidence rather than arithmetic -- but it is evidence of
#      "audio device open", not "set loaded", so it cannot simply replace the timer.
#   3. The real fix stays the known debt: an Ableton Remote Script that says READY.
#      ableton/readiness.py already has mark_confirmed_ready() waiting for it, and
#      calls the current state ASSUMED_READY precisely because of this gap.
